Codex → Joycode 缓存块超限分析

日期：2026-10-29（Asia/Shanghai）｜范围：只读诊断，未修改业务代码、配置或发送重放请求。

1. 结论与边界

该异常是上游请求校验失败：上游统计到 5 个 cache_control 块，但只允许 4 个。它不是上下文 token 超限，也不是 thinking signature 错误。

已关联到用户提供的精确 request id：本机出站请求只有 4 个 cache_control。所以“本地重复注入直接生成 5 个”的解释不符合此次证据。更可能是 Joycode 网关或其下游适配层补充/展开了缓存块；第 5 个块的确切位置尚未取得上游最终请求体，不能当作已证实事实。

4. 代码定位

  • src-tauri/src/proxy/cache_injector.rs：用 4.saturating_sub(existing) 限制新增预算。长历史可启用第 4 个较早 user 锚点；已有 >4 时仅警告并保留，不自动删 caller-owned 标记。
  • src-tauri/src/proxy/forwarder.rs:1795,1846：Codex → Anthropic 转换后注入；Joycode Anthropic 分支再调用。它不是完全幂等的：已有 3 个时可能再找一个更早消息并补到 4；但本次第二次调用没有超过 4。
  • src-tauri/src/proxy/forwarder.rs:1933–1960,4306：覆盖参数和私有字段过滤之后，对最终 body 递归统计 cache_control。该统计比注入器的顶层块计数更广，此次也只计到 4。
  • src-tauri/src/proxy/providers/joycode.rs:1808：当前 decorate_body 未添加缓存标记。

5. 最小验证与处置建议（未执行）

  1. 请 Joycode 按精确上游 request id 查询接入请求与实际下游请求，比较 cache_control 的 JSON 路径，确认额外块来自身份 system、自动缓存、块展开还是其他逻辑。
  2. 诊断实验优先限制到 JD Joycode + Codex + Anthropic 路由：将本地自动缓存预算临时降到 3，使用同一受控测试请求比较结果。若 4 失败、3 成功，可支持“上游另占一个槽位”的假设，但仍不能证明具体添加位置。
  3. 单纯关闭“较早 user 锚点”不足以保证只发 3 个，因为第二次 inject 可在历史中再补一个。应保证两处注入共享 3 个预算，或统一到唯一最终注入点。
  4. 必要时短暂关闭专用 cache_injection 开关排查；只关闭 optimizer.enabled 不够，Codex bridge 会强制 enabled=true。关闭缓存可能增加成本与首 token 延迟，也可能影响其他走同一配置的请求，不应直接修改用户配置。
  5. 若确认上游固定增加一个缓存块，再实施窄范围兼容策略及测试。不要全局删缓存标记，也不要改 thinking 内容、模型映射或其他供应商。

建议回归覆盖：0/3/4 个已有标记；短/长历史；两次注入；工具结果与 thinking 混合；cache_injection=false；其他供应商及非 Anthropic 路由不变。对同一错误原样重试不能消除结构性超限。

6. 官方规则

Anthropic Prompt caching 文档说明显式 cache_control 断点最多 4 个。此处未对 Joycode 的内部实现作官方事实断言。
