2. JoyCode 保留规则

本次采用“保留 JoyCode 专用实现、接受上游通用改进、用回归测试证明兼容”的规则，而不是机械地把所有重叠点改成 fork 旧值。

  1. JoyCode 专用实现必须保留：合并后 src-tauri/src/proxy/providers/joycode.rs 与 src/components/providers/forms/JoycodeConnectionFields.tsx 相对合并前 fork 侧无删除或回退。
  2. 本地网关前置判断必须保留：providerNeedsRouting 中 JoyCode 判断仍位于 official-provider 短路逻辑之前，确保 JoyCode 即使被标为 official 类别也仍经过本地代理。
  3. 目标供应商模型字段必须来自 JoyCode 配置：apply_claude_takeover_fields_for_provider 继续对 provider.is_joycode() 使用目标供应商配置生成模型显示名，避免菜单残留旧供应商。
  4. 上游通用别名变化需验证后接受：上游把接管稳定别名从 Sonnet 4.6 / Opus 4.8 提升为 Sonnet 5 / Opus 5。路由本身按角色关键词映射，因此不应为了旧测试期望而在生产代码中固化旧别名。
  5. 用测试锁住真实兼容关系：JoyCode 回归测试现在断言 claude-sonnet-5 → Claude-Sonnet-4.6-hq、claude-opus-5 → Claude-Opus-4.8-hq，证明新客户端别名仍会投影到 JoyCode 配置模型。

3. 语义冲突与处理

现象

Git 自动合并没有留下冲突标记，但完整 Rust 测试发现 1 个失败：

services::proxy::tests::joycode_claude_takeover_sources_migrated_models_from_provider
left:  Some("claude-sonnet-5")
right: Some("claude-sonnet-4-6")

原因

上游提交 38cfafdc 将 Claude Code 接管稳定别名升级为 claude-sonnet-5 / claude-opus-5。JoyCode 回归测试创建于旧别名时代，断言仍停留在 claude-sonnet-4-6 / claude-opus-4-8。

判定

这不是 JoyCode 生产能力被上游删除，而是测试期望过时。依据有三点：

  • ModelMapping::map_model 按 sonnet / opus 角色关键词选择目标模型，不要求客户端别名版本与上游目录版本一致。
  • forwarder.rs 先执行模型映射，再调用 JoyCode 的 resolve_model，保证进入 JoyCode 的是配置后的真实模型。
  • JoyCode 的供应商配置仍指向 Claude-Sonnet-4.6-hq 和 Claude-Opus-4.8-hq。

最小修复

只更新该回归测试的别名期望，并追加两个模型映射断言；没有为 JoyCode 增加生产分支，也没有把上游通用别名改回旧值，避免扩大影响半径。
